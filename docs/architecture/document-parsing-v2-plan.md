# 文档解析功能建设方案

> 目标：把现在的“解析示例”打磨成 All-Ontology 里可日常使用的文档工作台，
> 以及可校对、可检索、可交付的结果库。
>
> 范围：`all_ontology/parsing`、`frontend/components/parsingPage`、
> `frontend/app/api/parsing`、模型设置里的解析分组。
>
> 本方案只做 P0 + P1。知识本体/语义发布是独立项目，不在解析功能里继续扩展。

## 1. 结论

当前功能已经具备一条能跑通的解析链路：上传 PDF/图片、选择输出格式、异步任务、
Markdown/JSON/元数据预览、原始文件对照、磁盘实例列表、模型设置。它证明“能解析”，
但还不是一个“能放心交给业务使用”的功能。

建议不要再继续堆模型参数，而是按两步走：

1. **先做成可靠的工作台**：配置可自检、任务不丢、进度可见、失败可解释、可取消重试。
2. **再做成可校对的结果库**：原文与版面块联动、块级修订、重跑对比、批量导出。

建议节奏：P0 约 2–3 周，P1 约 4–6 周；P0 结束就应该能明显感觉到“顺手了”。
“解析结果进入知识本体”另立项目，复用这里产出的 Markdown、JSON（含 bbox）和块级修订。

## 2. 现有实现盘点

### 2.1 已经有的能力

| 能力 | 现状 |
| --- | --- |
| 输入 | PDF、PNG/JPG/WebP/BMP/TIFF，单文件或浏览器端多文件队列 |
| 解析链路 | PDF 渲染 → D-FINE 版面分析 → 阅读顺序 → OXR 识别 → 后处理 → Markdown/JSON |
| 选项 | 输出格式、页眉页脚、图片/公式/表格/化学结构格式、temperature 等 |
| 任务 | `POST /api/parsing/jobs` + 轮询，进程内 `MemoryTaskStore` |
| 结果 | Markdown、JSON（含 bbox）、元数据、原始文件四个页签 |
| 实例 | 每次解析落盘到 `<upload_dir>/<document>/<run>/`，列表按时间倒序 |
| 对照 | 批量页支持“原文 / Markdown”左右对照 |
| 设置 | 识别后端（none/vLLM/local）、版面服务、文件目录，保存后几秒生效 |

### 2.2 现在就能修的具体问题

这些问题不是“未来优化”，是当前就会让用户觉得功能不靠谱的点：

| # | 现象 | 根因/证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | 点“测试连接”，服务不可达也提示成功 | `/api/parsing/backends/test` 和 `/layout/test` 返回 HTTP 200，body 里才是 `reachable:false`；前端 `ParsingModelSettings` 只看 `response.error` | 用户以为配好了，真正解析时才失败 | 测试接口返回 `ok:false`（或前端显式判断 `reachable`），并显示具体错误 |
| 2 | “就绪”状态会误报 | `settings.status()` 的 `ready` 只判断两个 URL 是否非空，没有探测服务 | 页面显示可用，点解析才 503 | 区分 `configured` 与 `healthy`；进入页面时做轻量健康检查 |
| 3 | 页面展示了后端实际不接受的格式 | `capabilities()` 返回 `SUPPORTED_ELEMENT_FORMATS`，但 `build_options()` 只接受 `FUNCTIONAL_ELEMENT_FORMATS`；例如 `formula=mathml/ascii`、`table=image`、`image=file` | 用户选了就 422 | capabilities 只返回可用值，或把不可用项标灰并说明原因 |
| 4 | 解析失败会留下看不见的源文件目录 | 路由先 `create_instance()`，再 `submit_job()`；失败时没有 `result.json`，实例列表也看不到 | 磁盘持续增长，无法从界面删除 | 先做 readiness/输入校验；失败也写 `failed` 记录；增加孤儿清理 |
| 5 | 刷新或重启后任务丢失 | `MemoryTaskStore`，进程内字典，最多 200 条 | 重启即丢、多副本轮询 404 | 任务与进度落 Postgres，后台 worker 执行 |
| 6 | 只能看到“排队/解析中”，看不到做到第几页 | job 状态只有 `queuing/processing/success/failed` | 大文件用户不知道是否卡住 | 增加页级/阶段级进度，前端显示“第 8/24 页 · 识别中” |
| 7 | 失败只能整份重来 | 没有取消、重试、断点 | 100 页文档第 90 页失败成本很高 | 页级 checkpoint + 失败重试 + 取消 |
| 8 | “解析示例 / 创建批量解析任务”名不副实 | `/parsing` 是工作台，`/parsing/instances` 实际是结果列表；没有真正的“批量任务”实体 | 用户不知道去哪里找任务、结果 | 重划信息架构：工作台 / 任务 / 结果库 |
| 9 | 结果只能看 Markdown 和原始 JSON | JSON 有 bbox，但页面不画版面框，不能点块定位 | 校对只能靠肉眼来回找 | 原文叠加 bbox、块列表、悬停高亮、点击定位 |
| 10 | 实例列表每次全量扫盘，固定 100 条 | `list_instances()` 用 `glob("*/*/result.json")`，前端固定 `LIST_LIMIT=100` | 数据一多就慢，也找不到旧结果 | DB 元数据 + 游标分页 + 搜索/筛选 |
| 11 | 结果不可复现 | metadata 只有页数、耗时、实例 id，没有模型、版面服务、选项、pipeline 版本快照 | 同一份文件两次结果不同，无法解释 | 每次 run 记录完整快照 |
| 12 | 前端按文件轮询，1.2 秒一轮 | `BatchParsingView` 对每个 alive item 各发一次 job 请求 | 100 个文件约 80+ 请求/秒 | 批量状态接口或 SSE；至少合并轮询 |
| 13 | 代码有重复和死代码 | `ParsingView.tsx` 未被导出/使用；仓库里还有一份 `auto_ontology/parsing` 副本，运行中的服务实际使用 `all_ontology` | 后续改动容易改错地方 | 明确 `all_ontology` 为唯一实现，删除死代码与重复副本 |

> 第 13 条建议在 P0 第一周处理。当前 `start-dev.ps1` 启动的是
> `all_ontology.server.__main__:create_app`，所以后续方案默认以
> `all_ontology/parsing` 为准。

## 3. 产品目标

### 3.1 三个必须成立的结果

1. **第一次使用能在 10 分钟内成功解析一份文档**，包括配置、测试、上传、看到结果。
2. **结果可信且可追溯**：知道它来自哪份文件、哪个模型、哪组参数、哪个版本的解析链路；
   每个结论能回到原文位置。
3. **批量能交付**：100 份文档可以排队、看到进度、失败重试、批量导出；
   不会因为刷新页面或重启服务而前功尽弃。

### 3.2 这一版不做什么

- 不自研 OCR/版面模型，继续使用现有 OXR + D-FINE 能力。
- 不做完整 DMS（文档管理、版本库、权限树、全文检索）——只做解析工作台需要的部分。
- 不把低层模型参数继续暴露给普通业务用户；保留在“高级设置”。
- **不做本体抽取、术语映射和发布**；这些属于独立的知识本体项目，解析功能只负责把
  Markdown、JSON（含 bbox）和块级修订稳定地交出去。

## 4. 产品方案

### 4.1 信息架构

左侧二级菜单建议从两项改成三项：

| 菜单 | 路由 | 作用 |
| --- | --- | --- |
| 解析工作台 | `/parsing` | 新建解析、当前队列、即时结果 |
| 解析任务 | `/parsing/tasks` | 持久化的批量任务：进度、取消、重试、汇总 |
| 结果库 | `/parsing/library` | 所有历史 run：搜索、筛选、打开、导出、删除 |

兼容旧地址：

- `/parsing/instances` 重定向到 `/parsing/library`；
- `/parsing/instances/{document}/{run}` 保留，作为结果详情页；
- `/parsing/batch` 继续跳转到工作台或任务页。

“创建批量解析任务”是一个按钮，不再是一个菜单项；“解析示例”这个名字也建议退休。

### 4.2 主流程

```text
配置自检
  └─ 识别服务 ✓ / 版面服务 ✓ / 存储目录可写 ✓
       ↓
上传（拖拽/多选/分页范围）
       ↓
选择解析档位（快速 / 标准 / 高精度）
       ↓
任务队列（逐份、逐页进度）
       ↓
结果查看（原文 + 版面 + Markdown + 结构化）
       ↓
校对 / 重跑 / 导出
```

### 4.3 关键页面

#### 解析工作台

- 顶部：标题、后端状态胶囊（已配置/不可达/未配置）、`新建解析`。
- 左侧：上传区 + 当前队列；每个文件显示状态、页数、耗时、错误摘要。
- 中间：当前选中文件的原文预览，支持翻页、缩放。
- 右侧：结果页签（版面 / Markdown / JSON / 结构化 / 元数据）。
- 底部：任务操作（开始、取消、重试失败项、导出）。

#### 结果详情 / 校对模式

```text
┌──────────────────────────────┬──────────────────────────────┐
│ 原文（页码、缩放、缩略图）   │ Markdown / 结构化结果        │
│ ┌──────────────────────────┐ │ ┌──────────────────────────┐ │
│ │  bbox 高亮框             │ │ │ 标题                     │ │
│ │  点击块 → 右侧定位       │ │ │ 段落（可编辑）           │ │
│ │  悬停块 → 原文高亮       │ │ │ 表格（可编辑单元格）     │ │
│ └──────────────────────────┘ │ └──────────────────────────┘ │
├──────────────────────────────┴──────────────────────────────┤
│ 警告：表格 3 处回退为图片 · 公式 1 处可能截断 · 已校对 12/18 │
└─────────────────────────────────────────────────────────────┘
```

这个视图是“打磨”的核心：用户不是只看 Markdown，而是**在原文上确认结果**。

#### 任务中心

- 任务卡片：名称、创建人、文件数、完成/失败数、总进度、创建时间。
- 文件行：文件名、页数、当前阶段、页进度、耗时、错误码、操作。
- 操作：取消整个任务、重试失败文件、打开结果、导出任务汇总。

#### 结果库

- 搜索：文件名、任务名、文档类型、标签。
- 筛选：状态、日期、解析档位、是否已校对。
- 列表：分页、批量选择、批量删除、批量导出。
- 详情：保留 Markdown/JSON/元数据页签，并增加“版面/块编辑/修订记录”。

| ID | 功能 | 验收 |

失败知道为什么、能不能重试。

### 后续独立项目

模板化抽取、术语/表映射、本体发布、审核流和发布审计，另立“知识本体/文档入库”项目。
解析功能只负责稳定地产出：

- 块级 JSON（含 bbox、类型、格式、修订）；
- Markdown 与导出包；
- 模型/参数/版本快照，保证下游可以复现和追责。

## 6. 技术方案

### 6.1 目标架构

```text
Browser
  └─ Next.js BFF /api/parsing/*（认证、权限、审计）
       └─ FastAPI parsing routes
            ├─ 任务服务：创建任务、查询状态、取消/重试
            ├─ Postgres：task / document / run / block / profile
            ├─ Worker：领取任务 → 解析 → 写结果 → 更新进度
            └─ 文件/对象存储：源文件、页图、版面结果、Markdown/JSON、assets
```

建议把“接收请求”和“执行解析”分开：API 进程只负责入队和查询，独立 worker 负责执行。
这能解决重启丢任务、多副本不一致、长任务占用 API 进程三个问题。

### 6.2 数据模型

先加最小闭环表，输出正文仍可先放文件/对象存储，避免一次迁移全部历史数据：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `parsing_tasks` | id, name, created_by, status, profile_id, options_json, total, succeeded, failed, created_at, started_at, finished_at | 一次批量提交 |
| `parsing_documents` | id, task_id, file_name, sha256, size, mime, storage_key, page_count, status, error_code, error_message | 任务里的单个文件 |
| `parsing_runs` | id, document_id, attempt, profile_id, model_snapshot, layout_snapshot, pipeline_version, status, progress_done, progress_total, started_at, finished_at, quality_json, outputs_prefix, reviewed_by, reviewed_at | 一次实际解析 |
| `parsing_blocks` | run_id, page, idx, type, bbox, content, format, confidence, warnings, edited, edited_by, edited_at | 校对需要的块级数据；可先按页 JSON 存，P1 再拆表 |
| `parsing_profiles` | id, name, options_json, is_default | 快速/标准/高精度等解析档位 |
| `parsing_audit` | id, actor, action, target, before, after, created_at | 修订、删除、重跑的审计 |

实例 id 继续保留 `document/run` 作为兼容展示，但内部以 `run.id` 为准。

### 6.3 API 草案

保留现有接口，新增面向任务/结果的接口；旧接口标记为兼容层。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/parsing/tasks` | multipart 多文件 + profile/options，返回 202 + task_id |
| `GET` | `/api/parsing/tasks` | 任务列表，游标分页，支持状态/创建人/日期筛选 |
| `GET` | `/api/parsing/tasks/{id}` | 任务详情 + 文件级状态 + 进度 |
| `POST` | `/api/parsing/tasks/{id}/cancel` | 取消任务 |
| `POST` | `/api/parsing/documents/{id}/retry` | 重试单个文件（可指定失败页） |
| `GET` | `/api/parsing/runs` | 结果库列表，游标分页 + 搜索 |
| `GET` | `/api/parsing/runs/{id}` | run 详情（输出、快照、质量、校对状态） |
| `PATCH` | `/api/parsing/runs/{id}/blocks/{block_id}` | 保存块级修订 |
| `POST` | `/api/parsing/runs/{id}/review` | 标记已校对/退回 |
| `POST` | `/api/parsing/runs/{id}/reparse` | 用已存源文件重新解析 |
| `GET` | `/api/parsing/runs/{id}/export?format=zip\|html\|csv\|xlsx` | 导出 |
| `GET` | `/api/parsing/metrics/summary` | 成功率、耗时、失败原因、队列深度 |

任务提交支持 `Idempotency-Key`，避免用户重复点击或网络重试产生重复任务。

### 6.4 解析管线改造

当前 `process_document()` 是一次性黑盒。建议增加三个横切能力：

1. **进度回调**

```python
@dataclass
class ParsingProgress:
    stage: Literal["decode", "layout", "reading_order", "recognize", "assemble", "quality"]
    page_done: int
    page_total: int
    block_done: int = 0
    block_total: int = 0
```

在解码、版面批次、阅读顺序、逐块识别、装配后分别上报，worker 写入 `parsing_runs.progress_*`。

2. **取消与超时**

- 传入 `asyncio.Event` 或取消令牌；
- 在页循环、批次循环、块循环之间检查；
- 单页/单块设置超时，避免一个坏页面拖死整份文档；
- 取消后保留已完成页的结果，允许“从失败页继续”。

3. **页级 checkpoint**

把每页的版面块、识别结果、耗时写入 `runs/{id}/pages/{n}.json`；
失败重试只重跑未完成页，装配阶段再合并。这样大文件不必整份重来。

另外建议加一条**数字 PDF 快路径**：先检测 PDF 是否带可用文本层；有文本层的页面直接提取文本，
版面分析仍用于表格/图片/阅读顺序，识别模型只处理扫描页。对电子发票、报告类 PDF 通常能显著降本提速。

### 6.5 结果与质量信号

现有 `layout_score` 已经在 `Block` 上，建议把它和以下信号一起写进结果：

- `finish_reason=length`（可能截断）；
- 空内容、重复字符、异常短文本；
- 表格回退为图片；
- 公式 LaTeX 解析/编译失败；
- 块与块重叠、被去重删除的警告；
- 页面无任何块、识别服务重试次数。

前端用“警告”而不是“错误”呈现：用户仍然能拿到结果，但知道哪里需要重点校对。

### 6.6 存储

建议目录/对象键统一为：

```text
parsing/{task_id}/{document_id}/{run_id}/
  source.{ext}
  pages/0001.json
  outputs/markdown.md
  outputs/result.json
  assets/imgs/...
  manifest.json          # 模型、选项、版本、哈希、质量摘要
```

如果部署还没有对象存储，先抽象 `Storage` 接口，本地用共享卷，后续切 S3/MinIO 不改业务代码。
源文件和结果都应有保留策略；删除 run 时连同 assets 一起删。

### 6.7 前端改造

- 抽出共享的 `ParsingWorkspace` 状态，不再让工作台/批量页/详情页各自维护一套轮询和表单。
- 删除未使用的 `ParsingView.tsx`；批量页与单文件页复用同一个结果查看器。
- URL 承载 `task/run/page/tab`，刷新后能回到原位置。
- 轮询改为“任务级状态接口 + 进度字段”，或 SSE；避免按文件扇出请求。
- 查看器用绝对定位画 bbox：`left = x / page_width`、`top = y / page_height`，
  与现有 JSON 的 `page_size` 对齐；缩放只影响容器，不影响坐标比例。
- 表格校对优先做单元格编辑，不要一开始做富文本编辑器。
- 所有元素类型、错误码、状态补齐中英文文案；不要直接显示 `formula`、`cs`、`processing` 这类内部词。

### 6.8 权限与安全

当前解析相关 BFF 全部要求 `catalog: edit`，且实例列表是全局的。建议：

- 拆分权限：`parsing:read`、`parsing:write`、`parsing:publish`；配置仍归管理员。
- 结果按创建人/团队隔离；分享用带过期时间的签名链接。
- 上传做文件头校验、页数/像素上限、压缩炸弹防护、加密 PDF 识别。
- 模型/版面 URL 做 allowlist 或至少禁止内网任意地址扫描，避免 SSRF。
- 文档可能含 PII：接入现有 `pii_detection` 给出提示；保留策略、访问审计、删除能力要一起设计。
- 所有下载走签名 URL 或鉴权代理，不暴露服务器绝对路径。

### 6.9 可观测性

至少补齐这些指标：

- 任务队列深度、等待时长；
- 每阶段 p50/p95 耗时（解码/版面/识别/装配）；
- 成功率、失败原因 Top N；
- 单页平均耗时、模型 token 使用；
- 存储增长、孤儿文件数；
- 用户校对耗时、一次通过率。

日志里带 `task_id/run_id/page`，前端错误页显示可复制的 trace id。

### 6.10 共享文件夹批量

“新建解析任务”支持直接选择服务器/Windows 共享文件夹：

- 目录浏览复用 `FILE_SOURCE_ROOTS` 白名单（未配置时默认为仓库下的 `shared/`），
  不另外暴露任意磁盘路径；不跟随符号链接/目录联接。
- 选择文件夹后递归扫描 `.pdf`（大小写不敏感），默认单任务上限 1000 个，
  可用 `PARSING_MAX_SCAN_FILES` 调整。
- 每份 PDF 复制到解析上传目录后再入队，因此共享目录改名或断连不影响已建任务。
- 任务里每个 PDF 有独立的 `parsing_document`/`parsing_run`，页级进度折算成
  0–100% 的百分比显示；完成后自动出现在结果库，可按文件哈希对比上一版。

## 7. 质量评测

“打磨”不能只靠感觉。建议建立一个 50–100 份文档的金标集，覆盖：

- 电子 PDF、扫描 PDF、手机拍照；
- 中文/英文/中英混排；
- 单栏/多栏、表格、公式、代码、化学结构；
- 低清晰度、倾斜、印章、页眉页脚。

指标建议：

| 指标 | 说明 | 建议目标（需用金标集校准） |
| --- | --- | --- |
| 文本 CER/WER | 字符/词错误率 | 电子 PDF < 2%，扫描件 < 8% |
| 表格 TEDS | 表格结构相似度 | > 90% |
| 公式可编译率 | LaTeX 能被 KaTeX/MathJax 解析 | > 95% |
| 阅读顺序 | 相邻块顺序正确率 | > 95% |
| 一次通过率 | 不需要人工改块即可使用 | 电子 PDF > 95%，扫描件 > 85% |
| 任务成功率 | 不含用户取消 | > 99%（服务健康时） |
| P95 耗时 | 10 页文档 | 电子 PDF < 20s，扫描件 < 3min |

每次模型、提示词、后处理规则变更都跑回归；人工校对产生的修订自动进入评测集，
形成“使用越多越准”的闭环。

## 8. 里程碑与验收

### 里程碑

| 阶段 | 时间 | 交付 | 退出标准 |
| --- | --- | --- | --- |
| P0 | 第 1–3 周 | 配置自检、错误分类、持久任务、进度/取消/重试、IA 调整 | 重启服务不丢任务；失败可解释；测试连接不再假成功 |
| P1 | 第 4–9 周 | 任务中心、结果库、版面查看器、块级校对、重跑、导出 | 100 页文档可取消/重试失败文件；校对可定位到原文；批量可导出 |
按 1 名后端 + 1 名前端 + 0.5 名设计/测试估算；不含模型训练和基础设施大改。

### 验收场景

1. 新环境首次进入解析页：配置两个端点 → 测试通过 → 上传示例 → 10 分钟内看到 Markdown。
2. 上传 100 页扫描 PDF：看到页级进度；中途重启 API；任务按租约重新排队；不会丢结果。
3. 批量 20 份文件：其中 2 份失败；失败项有错误码和“重试”；其余可批量导出 zip。
4. 打开结果：点文本块 → 原文对应 bbox 高亮；改一个错字 → 保存 → 重新导出。
5. 同一份文件用“标准/高精度”各跑一次 → 打开两个 run 并排查看；逐行 diff 仍待补。

## 9. 风险与取舍

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 任务队列改造范围大 | P0 延期 | 先落 Postgres 任务表 + 单 worker；对象存储先抽象接口，本地卷可跑 |
| 大文件内存占用 | OOM/超时 | 页级处理、页范围、单页超时、DPI 档位、按页 checkpoint |
| 模型输出不稳定 | 结果不可信 | 质量信号、二次校验、重跑对比、金标集回归 |
| 文档含敏感信息 | 合规风险 | PII 检测、权限隔离、保留策略、审计、签名下载 |
| 功能越做越像 DMS | 范围失控 | 明确非目标；只做“解析→校对→导出”需要的文档能力 |
| OXR 上游/依赖变化 | 维护成本 | 保留移植边界与版本快照；把解析适配层与产品层分开 |

## 10. 建议先做的 5 件事

如果只排一个迭代，建议按这个顺序：

1. **修“测试连接/就绪状态”**：让配置页说真话，这是信任的起点。
2. **任务落库 + 页级进度 + 取消/重试**：解决“刷新就没了”和“卡住不知道”的两个最大抱怨。
3. **重划信息架构**：工作台 / 任务 / 结果库，先把“解析示例”这个演示感名字换掉。
4. **做 bbox 版面查看器 MVP**：原文与结果联动，让校对从“猜”变成“看”。
5. **补 run 快照 + zip 导出**：让结果可复现、可交付。

这五件事完成后，解析功能的 P0/P1 就形成闭环；模板抽取和本体发布另立项目推进。

## 11. 需要拍板的几个问题

下面几项会影响实现顺序；方案里已经给出默认建议，确认后就可以直接排期：

| 问题 | 建议默认 | 影响 |
| --- | --- | --- |
| 部署是单副本还是多副本？ | 按多副本设计：Postgres 任务表 + 独立 worker | 单副本可以先简化，但不要再用进程内任务 |
| 文档是否含敏感信息？ | 默认按敏感处理：权限隔离、审计、保留期、PII 提示 | 决定是否要在 P1 就接 `pii_detection` |
| 是否需要 Word/PPT/Excel？ | 本方案先聚焦 PDF 与图片，其他格式另排 | 提前做会显著增加格式适配与版式还原成本 |
| 谁负责校对？ | 解析创建人校对，管理员抽查 | 决定 P1 的校对权限与列表筛选 |
