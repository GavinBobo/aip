# Ontology-Studio 产品方向与路线图（2026）

## 1. 一句话定位

**Ontology-Studio 不是“文档库 + 数据字典”，而是企业智能体的语义控制面：让 Agent 在回答和执行之前，先拿到经过治理的定义、指标、规则、证据和权限边界。**

产品价值不在于“能抽多少概念、能画多少表”，而在于把下面这条链路跑成闭环：

```text
数据源 / 文档 / API
        │
        ▼
   语义建模与候选生成
        │
        ▼
   人工审阅 / 认证 / 发布
        │
        ▼
   检索 / 问数 / 解释 / 规则检查
        │
        ▼
   使用反馈 / 评估 / 版本迭代
        │
        └──────────────► 回到建模
```

## 2. 现有产品判断

当前产品已经具备很好的底座：

- **数据侧**：目录摄取、术语、列属性、SQL 属性、指标、语义外键、ERD、探索、发现、分析、Chat；
- **文档侧**：PDF/图片解析、概念/关系/事实/动作/风险/指标、页码与块号证据、知识图谱、BKN 导出/导入；
- **治理侧**：Zone、用户/部门授权、标签、负责人、认证、PII、MCP 只读工具；
- **新增能力**：ERD → 数据本体候选、知识检索服务、文档 chunk 检索、Human/Agent 两种检索策略。

但产品目前仍然是“多个能力页面的集合”，还没有形成完整的语义运营闭环。主要缺口是：

1. **两层本体没有真正打通**：概念能映射到术语/表，但指标→SQL 属性、规则→指标/字段、动作→工具能力还没有成为完整链路。
2. **业务规则没有一等对象**：制度里的“超过 1 万元需审批”现在只能落在事实、动作、风险里，缺少可版本化、可检查、可解释的规则对象。
3. **自动建数据本体还是一次性报告**：缺少候选批次、差异、审批、发布、回滚的完整工作流。
4. **知识检索还不够生产级**：目前是词面召回，缺少向量召回、rerank、冲突处理和更多文档连接器。
5. **评估还不是产品能力**：现在主要验证“检索有没有命中”，还没有系统验证答案正确性、引用正确性、SQL 有效性、权限泄漏和跨层推理。
6. **Agent 执行仍是 dry-run**：动作计划有了，但缺少隔离执行、审批、策略拦截和执行审计。

## 3. 产品飞轮

未来所有功能都应该服务于这个飞轮：

```text
Ingest → Propose → Review → Certify → Serve → Observe → Improve
```

| 环节 | 产品能力 | 成功标志 |
| --- | --- | --- |
| Ingest | 数据库、文档、API、文件接入 | 核心数据与文档可增量同步 |
| Propose | ERD/目录/文档自动生成候选 | Agent 能提出有价值的实体、指标、关系、规则 |
| Review | 候选批次、差异、冲突、影响分析 | 业务专家能低成本审核 |
| Certify | 认证、版本、发布、回滚 | 每条语义资产都有负责人和状态 |
| Serve | 检索、问数、解释、规则检查、MCP | Agent 能拿到可信上下文 |
| Observe | 使用日志、评估、反馈 | 知道哪些定义被使用、哪里答错 |
| Improve | 从失败问题反推模型缺口 | 语义覆盖率持续提升 |

## 4. 四个产品面

### 4.1 Ontology Studio：建模工作台

不是按“页面”组织，而是按“资产生命周期”组织：

- 数据本体：目录 → 术语 → 列属性 → SQL 属性/指标 → 语义外键 → ERD；
- 知识本体：解析 → 概念/关系/事实/动作/风险 → 证据 → 审核；
- 规则层：规则、阈值、适用范围、例外、生效时间、责任人、证据；
- 桥接层：概念↔术语/表、指标↔SQL 属性、规则↔指标/字段、动作↔工具。

ERD 继续作为数据本体的**设计先验**，但必须明确：

- `table_id` 有值：可查询、可编译；
- `table_id` 为空：虚拟表，只能作为设计意图和候选；
- ERD 与 catalog 的差异要生成报告，不自动覆盖任何一边。

### 4.2 Semantic Gateway：语义网关

统一承接人和 Agent 的消费：

- 人：知识检索、术语查询、指标解释、影响分析、ERD 探索；
- Agent：`retrieve`、`resolve_term`、`get_metric`、`validate_sql`、`explain`、`check_policy`；
- 两种检索策略：Human 覆盖草稿；Agent 只取已审阅/已认证；
- 所有结果返回来源、版本、页码/块号或 SQL 证据；
- MCP 与 REST 共用同一套语义结果结构。

### 4.3 Governance Center：治理中心

把认证、权限和变更做成产品流程：

- 资产生命周期：draft → proposed → reviewed → certified → published → deprecated；
- 变更请求：一次变更同时影响数据本体、知识本体、规则和桥接；
- 差异与影响分析：改一个指标会影响哪些问题、哪些 Agent、哪些报表；
- 权限：Zone、用户/部门、列级 PII、未来的行级策略；
- 审计：谁改了什么、为什么改、依据是什么、何时生效。

### 4.4 Quality Lab：质量与评估

“高准确率”必须被测量，而不是靠感觉：

- 文档问题：检索召回、引用正确性、答案正确性、拒答率；
- 数据问题：SQL 可执行率、结果正确性、join 路径正确性；
- 跨层问题：概念能否落到术语/表/指标，规则能否被检查；
- 权限问题：检索和 SQL 是否泄漏越权内容；
- 版本回归：每次发布前后跑同一套黄金问题。

## 5. 规则、指标、知识怎么分工

这是产品必须明确的产品原则：

| 对象 | 回答的问题 | 归属 |
| --- | --- | --- |
| 概念/事实/证据 | 文档里是什么、依据哪一段 | 知识本体 |
| 规则/政策 | 谁在什么条件下必须/禁止做什么 | 知识本体的规则层 |
| 指标 | 多少、怎么算、什么粒度/单位 | 数据本体 |
| 字段/表/关系 | 数据在哪里、怎么 join | 数据本体 |
| 动作 | 可以执行什么、需要什么参数 | 知识本体 + 能力层 |

**不能把业务规则塞进指标。**  
“超过 1 万元需财务总监审批”是规则；`approval_compliance_rate` 才是指标。规则引用指标，指标不替代规则。

建议的规则对象最小字段：

- `statement`：自然语言规则；
- `scope`：适用对象/组织/数据范围；
- `condition`：可计算条件；
- `roles`：审批/责任角色；
- `exceptions`：例外；
- `effective_from/to`：生效时间；
- `evidence`：文档页码/块号；
- `status/version/owner`：治理状态。

## 6. 分阶段路线图

### P0：把“桥”做实（最高优先级）

目标：让两层本体真正连起来。

- 概念 → 术语/表；
- 指标 → SQL 属性；
- 规则 → 指标/字段/动作；
- 动作 → 工具能力；
- 桥接覆盖率看板与未映射队列。

验收：选 10 个核心概念、5 个指标、3 个动作，完成映射；三类问题可回答。

### P1：知识检索生产化

目标：从“能搜”到“可依赖”。

- 文档连接器：Word/PPT/HTML/Confluence/邮件/Wiki；
- 混合检索：关键词 + 向量 + rerank；
- 文档版本、去重、冲突提示；
- Human/Agent 两个检索画像；
- 引用、页码、块号、权限过滤；
- Discovery 增加知识结果类型。

验收：黄金问题集上召回率、引用正确率、拒答率达标；不同权限用户看不到越权内容。

### P2：数据本体候选工作流

目标：把 ERD → 数据本体从“一次性报告”变成可运营流程。

- 候选批次持久化；
- ERD/catalog 差异；
- 候选实体/关系/指标/术语的审核；
- 批量应用、回滚、来源追踪；
- 规则/指标建议与人工认证。

验收：20 张核心表完成候选 → 审核 → 编译；认证覆盖率可量化。

### P3：规则与跨层检查

目标：让制度真正约束 Agent 行为。

- 规则对象与版本；
- `check_policy` 只读检查 API；
- 规则 → 指标/字段 → 证据的链路；
- 跨层评估：制度 + 数据 + 指标；
- 规则冲突、例外、生效时间。

验收：能回答“按制度，哪些订单需要审批”，并给出规则、数据、证据。

### P4：Agent Gateway 与安全执行

目标：从“给上下文”到“安全执行”。

- 统一 MCP/REST 工具：`retrieve`、`resolve_term`、`validate_sql`、`check_policy`、`explain`；
- 动作 dry-run → 审批 → 隔离执行；
- 执行前策略检查、执行后审计；
- 工具能力注册与参数绑定。

验收：高风险动作必须经过策略/审批；执行可追溯。

### P5：规模化与价值运营

目标：从“能用”到“可运营”。

- 增量同步、变更影响分析；
- 数据资产价值评分：关键性、使用度、下游依赖、质量、治理；
- 语义覆盖率、认证率、复用率、Agent 使用率；
- BKN 互操作与外部生态；
- 多团队、多 Zone、细粒度权限。

## 7. 先做什么、不做什么

### 先做

1. **桥接层**：没有它，两套本体只是两个孤岛。
2. **知识检索质量**：没有引用和召回质量，知识本体无法成为可信底座。
3. **候选工作流**：自动生成必须可审核、可回滚。
4. **规则对象**：业务约束不能降级成指标。
5. **评估体系**：没有黄金问题集，就无法证明“高准确率”。

### 不要先做

- 不要先做通用规则引擎；先用规则对象 + 高价值场景验证。
- 不要先做全量企业铺开；先做一个业务域。
- 不要让 Agent 自动发布语义资产；必须是候选 + 认证。
- 不要把 ERD 当物理真相；它只是设计先验。
- 不要把知识本体当全文索引；它是语义层，检索是消费方式。
- 不要把制度塞进指标；规则、指标、动作各自建模。

## 8. 北极星指标

| 指标 | 含义 |
| --- | --- |
| Trusted Answer Rate | 有认证定义、有证据、通过权限校验的答案比例 |
| Semantic Coverage | 核心表/文档中已认证语义资产的比例 |
| Bridge Coverage | 跨层问题中能落到术语/表/指标的比率 |
| Citation Accuracy | 文档答案引用页码/原文正确的比例 |
| SQL Validity | 生成 SQL 通过校验并可执行的比例 |
| Change Lead Time | 源变化 → 语义资产更新的时间 |
| Agent Reuse | 语义资产被 Agent/分析复用的次数 |
| Permission Incidents | 越权检索/查询事件数，目标为 0 |

## 9. 结论

未来的 Ontology-Studio 应该少做“又一个页面”，多做“语义资产的运营系统”：

> **数据本体负责“怎么算”，知识本体负责“依据什么”，规则层负责“允许/禁止什么”，语义网关负责“让 Agent 正确使用”，治理与评估负责“让它长期可信”。**

这条路线比“继续增加更多抽取模型和更多图谱页面”更难，但它才是企业智能体真正需要的底座。
